# SQLite storage

`database.ts` owns `node:sqlite`, connection settings and write locks. `schema.sql` is the starting schema, copied unchanged from the normative specification; the schema test compares both the text and the resulting tables/indexes. There are seven application tables and no triggers.

## Opening

- `Database.initialise(path, initial, options)` deliberately creates an absent or zero-length regular file. It records a generated database UUID and the supplied resolved configuration in the same transaction as the schema. It never adopts a nonempty file. The database may have an explicit location outside the state directory, but must remain inside the trusted retained root.
- `Database.open(path, options)` defaults to read-only. Missing databases give `not_initialised`. It checks family and version using a read-only connection before any persistent pragmas or exclusive-creation probe. Unsupported families/versions are not migrated or rewritten. Version 1 has no preceding supported schema to migrate.
- A writable open uses `{ ...options, readOnly: false }`. All write methods recheck family/version under `BEGIN IMMEDIATE`. Future migrations and domain operations must extend admission checks here, not bypass them with another connection owner.
- Use `using database = await Database.open(...)`, or close it in `finally`. Failed opens and failed initialisations close their connections. Transaction failures roll back before returning; the connection remains usable.

The trusted host supplies `options.location`: an existing canonical `retainedRoot` on local storage and the complete inventory of `recyclableRoots`. The database must be below the retained root and outside every recyclable root. Neither workers nor task text may choose this policy. Parents must already exist. Paths must be absolute, canonical and free of symbolic links; database hard links and non-regular files are refused. The opener checks exclusive creation on writable paths and refuses known network filesystem types. Other filesystems' locality is a host precondition: there is no portable API that proves a filesystem is retained, local or durably backed. Directory ownership must prevent concurrent untrusted path replacement; `node:sqlite` opens a pathname, not an already-verified file descriptor.

Read-only opens do not create directories, database files or probe files. They do not change journal mode; a recognised database not in WAL mode needs a writable open first. SQLite may manage its normal WAL/shared-memory sidecars. A live WAL database must be backed up with SQLite's backup API or checkpointed and closed, not copied as a single file.

## Transactions and evidence

`appendEvents` is the narrow insert-only evidence operation. It inserts a batch atomically, generates event IDs, preserves recording order and compares duplicate source keys by logical JSON content. Conflicting duplicates or relational constraints refuse the whole batch. There is no event update/delete/replace method and no public raw SQL or transaction callback API. Domain-specific payload validation, authority and state transitions belong in typed operations as they are added; generic event storage does not grant authority or validate all future event families.

Transaction callbacks are internal and synchronous. They may only perform database work: never await filesystem operations, processes or providers while holding a lock. Busy admission retries yield to the event loop, with a finite deadline (default 5 seconds, configurable up to 60 seconds). SQLite's own busy timeout is zero. Callback failures roll back, including a defensive refusal of Promise/thenable returns. Open retries also use fresh connections for transient Windows `SQLITE_IOERR_TRUNCATE` failures after an unclean exit.

## Tasks

Task types are in `tasks.ts`; `Database` owns all task SQL. These in-process methods do not add CLI commands. The host supplies a person actor (`{ kind: 'person', id }`), separately from task input. This is attribution, not a replacement for future host permission checks.

- `addTask(input, actor)` accepts a title and optional ID, instructions, ordered text criteria, kind, profile, objective ID and blocker IDs. Defaults are queued, unheld, code, empty instructions/criteria, no profile/objective, definition revision 1 and decision revision 0. Generated IDs use a readable title slug, then `-2`, `-3`, etc. Explicit collisions refuse; identities have no deletion/reuse method. New tasks go after the current last position.
- `updateTaskDefinition(id, patch, actor)` accepts only definition fields. One effective edit increments the definition revision once, even when several fields change. Criteria order matters. Equal values and empty patches do nothing.
- `addBlocker` and `removeBlocker` take task ID, blocker ID and actor. Both IDs must exist; self/cyclic additions refuse. Duplicate additions and absent-edge removals do nothing. Dependencies affect readiness, not revisions or dependant states.
- `reorderTasks(ids, actor)` takes a complete permutation. Positions remain positive and unique, including during the transaction; unchanged order does nothing.
- `holdTask(id, reason, actor)`, `releaseTask`, `markTaskDone` and `reopenTask` increment the decision revision only when their decision changes current fields. A hold reason is one nonblank line of at most 200 characters. State decisions preserve holds; hold/release preserve state. Done is a recorded person judgement, not accepted output. These methods never set in_flight; that belongs to the future start operation.
- `task(id)`, `tasks()` and `readyTasks()` return detached snapshots, with blocker IDs in ID order and tasks in position order. Ready means queued, unheld and all blockers done. Unknown task IDs refuse rather than yielding an empty task.

Every effective operation writes one `action.recorded` event in the same `BEGIN IMMEDIATE` transaction as its rows. Definition and decision updates match the revision read under that lock and require one affected row. No-op operations emit no event. All caller-owned inputs are detached before waiting for the write lock. Definitions, graph checks and end-position/ID allocation are decided under the lock. The operation tests inject failure both before and after event insertion for each task write method, then inspect through a fresh connection to prove all-or-none persistence.

## Claims and requests

Types and input validation live in `claims.ts` and `requests.ts`; all SQL stays in `Database`. These are in-process storage methods, not CLI commands or attempt operations. The trusted host supplies actors, callers, claim generations and evidence. Storage checks identity and transitions, not the truth of external evidence or future operation-specific permissions.

- `registerClaims(inputs, actor)` generates permanent UUIDs and inserts all resources in resource-key order under one write lock. Every input records its role, optional attempt/objective scope, generation, owner reference, schema family/version, configuration revision and heartbeat. Schema/configuration must match the database. A worker owner names `worker:<attemptId>`; an attempt and objective must agree. Any unreleased resource refuses the entire batch, regardless of heartbeat age.
- `refreshClaim({ claimId, generation }, heartbeatAt, actor)` updates only that unreleased owner. `releaseClaim(identity, evidence, actor)` requires nonempty JSON evidence and retains it with the release time. Both compare the claim revision and recheck schema/configuration under the write lock. No method adopts, transfers, expires or deletes a claim. `claim(id)` and `claims()` include released history.
- `heartbeatStatus(value, nowMs)` is a pure rule: age 0 through 29,999 ms is fresh; age 30,000 ms is stale. Future-dated and unreadable values are distinct non-fresh reasons. Scheduling the 5-second heartbeat is the host's responsibility.
- `recordCommand(input)` stores a stable key, operation, logical JSON caller, fingerprint and immutable input. Repeating the key with the same operation/caller/fingerprint returns the original, including its original input. A mismatch returns `request_input_mismatch` without changing anything. The caller must derive the fingerprint from its complete logical input.
- `recordEffect(input)` links an effect to a command from the same caller, fixes its executor claim/generation and stores immutable input and a typed target (`workspace`, `worker`, `answer`, `checks`, `repository` or `diagnostics`, with a JSON reference). Replays must match all effect fields. Scope must agree with the executor and any attempt. The pending request already names its recorded owner; this does not grant permission to call it.
- `claimEffect(id, identity)` moves only pending to claimed, records the claim time and generation evidence, and requires the recorded unreleased executor and a fresh heartbeat. `closePendingEffect(id, 'withdrawn' | 'rejected', result, caller)` requires the original caller. `recordEffectOutcome(id, identity, 'succeeded' | 'rejected' | 'uncertain', result)` moves only claimed effects and requires their exact executor. Results are nonempty JSON evidence and are recorded once. Terminal/uncertain outcomes cannot be reopened or overwritten; reconciliation is a separate future operation.
- `request(id)` and `requests()` return detached snapshots. `admissionBlockers(nowMs)` takes one read snapshot and reports every non-fresh unreleased claim and every uncertain effect, naming its ID and reason. A claimed effect blocks only if its executor claim is released, missing or not fresh; a fresh unreleased executor represents work in progress. The read never changes state. Reservation and activation operations must use the same admission rules within their own write transaction; an earlier read is not permission to launch.

Every change has a `claim.*` or `request.*` event in its transaction. Duplicate recordings return their original without a new event. Fault-injection tests cover each transaction before and after event insertion, including failure after the last event of a multi-resource batch. Operations use real temporary databases. Claim uniqueness and reservation races use independent processes, synchronised at explicit barriers.

## Attempt reservation and allocation

`reservations.ts` defines the reservation, trusted check evidence and allocation inputs. `reserveAttempt(input)` compares the request key's logical task selection, profile, source attempt, note and caller before checking current policy or readiness. Matching repeats return the original attempt's current progress, without resolving commits again. A new key selects the named eligible task or the first eligible task by position under one write lock. Readiness, revisions, lifetime attempt count, retained leases, context capacity and admission blockers are checked in that transaction. Objective-linked tasks and continuation are refused until their operations exist. The host currently supplies a person caller, as for task operations.

The latest recorded `context.configured` event supplies limits, base and target branches, finalisation and strict named profiles. Dispatch profile overrides task profile, then the kind default. Trusted repository code supplies the exact starting commit and check set with source commit/digest; `reserveWithTrustedChecks` resolves that policy through the repository adapter. The immutable specification records those inputs and their configuration/profile sources, task definition and revisions, delivery contract, repository/workspace identity and a database/attempt-qualified output ref. It contains no raw environment or credential configuration.

`beginWorkspaceAcquisition` checks the command/caller and fresh, unreleased executor, then records and claims one `workspace.acquire` effect. An existing acquisition request never grants permission to call again, regardless of its outcome. `recordAllocation` compares holder, pool, repository, ref and actual starting commit against the specification, accepts the provider's absolute, normalised path strictly inside that pool, then records the immutable lease/allocation and successful effect together. The specification stores the holder and pool, not a predicted workspace path. An identical repeat returns the recorded allocation; changed content refuses. `recordUncertainAcquisition` records unknown lease state and inspection evidence together with the uncertain effect, without requiring a lease ID.

`../attempts.ts` orchestrates reservation and the fake-or-real workspace provider outside transactions. A repeated command only reads progress and never acquires another workspace. A thrown provider call or refused confirmation retains the request, available response and provider evidence for inspection. There is no workspace adapter or CLI dispatch yet. Transaction tests inject failure before the first and after the last event of each new write; process tests cover capacity two, one reservation per task and stable-key replay.

## Worker launch admission

`launch.ts` defines the trusted bb worker reference and host binding used by the internal launch methods. An allocated attempt must already exist. A bb plugin caller is not implemented yet; these methods are not CLI operations.

- `registerWorkerOwner` records the one active `worker_owner` claim for an allocated attempt; `heartbeatWorkerOwner` refreshes it while fresh. A stale claim cannot be renewed by heartbeat.
- `bindWorkerReference` records the bb thread ID and matching owner claim together. Repeating the exact binding has no effect; a different thread or claim is refused.
- `decideWorkerLaunch` commits either permission or a fence. Permission rechecks task definition and readiness, changes the task to `in_flight`, and creates one pending `worker.activate` effect in the same transaction. A fence cannot be reversed into permission.
- `admitInitialBbPrompt` is for the enabled plugin's dispatch hook. It atomically claims the pending activation effect before returning `admitted`. A repeated call returns `already_admitted`, including after reopening the database. If the hook crashes after this claim but before bb receives its answer, the effect remains unresolved and no second prompt is authorised.

Each write checks the active owner claim, schema and configuration version, and its fresh heartbeat. Current-field changes and their events commit together. The launch operation tests seed allocated attempts at the fixture boundary to isolate the binding and launch race. These methods do not yet qualify the bb launcher: the real workspace/launcher adapters, effect reconciliation, terminal fence and host restart cases remain to be implemented and tested.

## Worker results and completion

`results.ts` defines the version 1 worker result and observation validation rules. Reservation freezes `resultPath` at `<stateDirectory>/attempts/<attemptId>/result.json`; preparation records that path and the internal session UUID before binding a worker. The host creates private retained directories outside recyclable roots. `workerResultBinding(attemptId)` returns the exact identity, refs, ordered criteria and delivery requirements to include in a result.

The result is a strict JSON object with these fields:

- `version: 1` and `identity: { databaseId, contextId, taskId, attemptId, leaseId, sessionId }`.
- `startingCommit` and `outputRef`, matching the stored attempt.
- `outcome: completed|held|failed`, a nonblank `summary`, and `reason` (null for completed, nonblank for held/failed).
- `criteriaReport`: every stored criterion once as `{ position, criterion, status: met|not_met, evidence }`. Positions count from 1; text matches exactly. Array order need not match position order. These are worker claims, not independent acceptance evidence.
- `evidence`: named `{ name, summary }` records, including every required evidence name.
- `workReferences`: named Git `{ kind: git, name, branch, commit }` or artefact `{ kind: artefact, name, path, description }` records, including every required deliverable name. Git branches match the full output ref. Artefact paths are relative to the retained result directory, without traversal or links.

`validateWorkerResult(attemptId, host, repository)` checks a regular, unlinked source of at most 1 MiB, all identities and contract fields, and retained artefacts. Completed code needs one exact commit strictly descending from the starting commit, with confirmed ancestry and retention from the repository adapter. It records content, source SHA-256, relative path, validation version/time and artefact SHA-256 digests in one immutable `attempt.result_validated` event. Repeated validation reads the files again and returns that original event; changed or missing source/artefacts produce `result_discrepancy`, never replacement evidence. Filesystem reads and repository queries happen outside the SQLite write lock; the binding and owner are rechecked under it. As with database paths, trusted directory ownership must prevent concurrent untrusted parent replacement.

`recordWorkerObservation(observation, host)` accepts a bound worker's turn-end, result-available, terminal or internal idle observation. Source ID/sequence pairs are immutable and deduplicated. Old sequences are retained because independent facts can arrive out of order. Pi terminal proof names direct child exit; bb terminal proof includes durable refusal of later turns. Neither is a claim that child processes have stopped. Unknown or mismatched host/worker identities and unsupported payloads refuse.

`../workers.ts` exposes `observeWorker` to retain observations before processing results. Result-available observations trigger validation. A valid result without terminal evidence stays execution-open, as does terminal evidence without a validated result. Idle, turn-end and a file merely existing never suffice. Invalid result processing does not roll back an already recorded terminal observation, so a later valid result can finish the attempt.

`completeWorker` rechecks the files, then atomically records the outcome, candidate, task change and `attempt.completed` event once. Completed code selects the exact validated commit and holds the task for acceptance; a retained report completes its task. Held/failed outcomes hold the task without inventing a candidate. Every task change is conditional on the decision revision captured at start, so a newer person hold, done or reopen wins. Candidate identity is exposed in `attempt().candidate`. Completion neither accepts nor integrates output, runs mandatory checks, returns a lease, releases the owner nor confirms that no processes remain. Checks, review verdicts, acceptance and return remain separate operations.

## Candidate checks

`reserveWithTrustedChecks` in `../attempts.ts` resolves the target branch's `.docket/checks.json` through `GitRepository.readCheckPolicy`, then freezes the effective repository/context definitions in the reservation. It checks the configuration revision again under the reservation lock. Replays return the original reservation without reading a new policy. The lower-level `reserveAttempt` still accepts already resolved trusted evidence; workers must never supply it.

`runCandidateChecks` in `../checks.ts` requires a recorded candidate, terminal worker and validated result. The host supplies the person caller, a non-secret execution profile identity with tool/dependency versions, the repository adapter and a check runner. `checkCommandRunner` takes the profile's explicitly resolved environment and known credential values for redaction, separately from the evidence identity. It never inherits an environment implicitly, strips `DOCKET_` names, disables the shell and closes stdin. It bounds diagnostics; an overflowing stream is suppressed rather than exposing a partially captured credential.

The operation reads the current trusted policy and requires the union of recorded and current definitions. It snapshots the declared profile before asynchronous reads and rechecks the context configuration revision/digest under the admission lock; a concurrent configuration change refuses before claiming a slot. Its evidence key covers repository, exact commit, copied criteria, definitions, effective policy digests and profile identity. Source commits remain provenance, not part of that key. A matching pass is reused; automatic calls also reuse failure. An explicit new request key can retry a failure, but replaying that request cannot execute again. Empty mandatory sets are visible in the stored input and produce an explicit result after workspace verification.

`beginChecks` atomically records the request and acquires a `check_executor` claim subject to `maxConcurrentFullChecks` (default 1). A pending request with an `awaiting_checks` attempt is waiting, not permission to run. The host can call again when capacity changes. Runs execute fast checks then full checks serially, checking the repository, candidate and tracked/untracked state before, between and after commands. Check-specific Git inspection disables fsmonitor/untracked-cache shortcuts and refuses assume-unchanged/skip-worktree entries. Ignored generated files are allowed only by the execution profile's declared paths or glob patterns; other ignored files refuse check admission.

`finishChecks` stores results and releases a slot only after a confirmed pass or failure. A signal kill or interrupted observation remains uncertain and keeps the claim; a lost executor leaves its claimed request and slot unresolved. Heartbeat age never frees either. Reconciliation remains an explicit owner/person operation, not automatic retry. A failure holds the task as `checks_failed`, conditional on its original person-decision revision. An uncertain result uses `checks_uncertain`. Neither checks nor reuse waive review or accept output.

`observeWorker` accepts optional trusted check services and caller attribution. With them, completion of a code candidate invokes this same check path. Without them, it records completion only; a host must call `runCandidateChecks` before acceptance. These are internal APIs, not new CLI commands or supervisor permission grants.

## Acceptance, return and discard

`../completion.ts` exposes person-only `selectCandidate`, `acceptCandidate` and `returnAttempt` application operations. These are internal APIs, not additional CLI commands. Acceptance names both the candidate ID and exact commit. A selected retained output commit gets a fresh candidate ID; an accepted candidate cannot be replaced. Acceptance revalidates retained output, uses matching mandatory fast/full checks, re-resolves current check requirements, and records the candidate, evidence request, finalisation plan and current person-decision revision together. A nonblank person override reason is retained against that candidate and can bypass missing/failed checks, but not terminal state, identity, retention or unresolved effects.

Integration is a separate repository effect before task completion. Manual acceptance records a deliverable only. Local integration uses the planned target's exact old commit, or records that it already contains the candidate. A newer person decision prevents a pending integration and is never overwritten by task completion. Replays inspect recorded acceptance, effect and completion events rather than repeating a completed step.

Return requires the exact lease's person no-processes confirmation, terminal/stopped execution, a matching allocation/pool, a recorded outcome, retained result/artefacts and no unresolved effect. Discard additionally requires an explicit confirmation and nonblank reason, holds unfinished work, and preserves done decisions. Authorisation, conditional lease return, confirmed returned state and optional ref cleanup are separate steps. Manual-unintegrated output remains retained. Cleanup failures cannot reverse return.

Completion effects have their own maintenance claims and immutable typed targets. Definite success/refusal releases the claim atomically with its result. A claimed or uncertain effect is never called again: owner reads can settle exact target reachability, an absent lease in its original pool, or an absent output ref. Otherwise explicit resolution is required. A read failure before claiming an effect can be retried without another external call. No SQLite write lock is held during owner reads, checks or workspace/repository effects.

## Durability and qualification

Every connection requests foreign keys, synchronous FULL, fullfsync and checkpoint_fullfsync. Writable connections establish WAL; read-only ones require it. `settings()` exposes requested SQLite settings, not a proof of hardware durability. SQLite's full-fsync options have additional effect on macOS where supported; other OS/filesystem combinations can provide only their ordinary sync guarantees. Network filesystems are unsupported. Devices, virtualised storage and filesystems can still fail to honour sync requests. No stronger power-loss guarantee is claimed.

The default tests cover schema inspection, byte-preserving refusal, path admission, settings, bounded asynchronous contention, event rollback and a real child process killed inside a reservation transaction. The crash fixture alone reaches private transaction machinery for fault injection; it is not an application SQL interface. A second process reopens and commits after the kill, and the test checks for partial rows and database integrity. These tests were run locally on macOS; CI runs the same suite on macOS, Linux and Windows. Host/filesystem qualification and future migration protocols remain separate work.
