# Detached execution: findings on the existing code

These findings support the [detached execution plan](detached-execution.md). They record what the existing foreground implementation does on each path the [detached specification](../specification/detached.md) needs, which parts to keep, and which tests preserve them. They are not part of the specification. The code was traced at `58177a0` and the findings rechecked against `d6e9f65`.

The paths are numbered in the order of the worked example in the specification's [acceptance scenarios](../specification/detached.md#acceptance-scenarios): A and B dispatched (D01), status (D02), A delivered by fast-forward (D03), B by PR (D04). An existing test is evidence of what Docket does today, not a reason to require that behaviour in the new workflow.

## Summary

the transaction, Git operations, check runner and lease identity checks can be retained. Reservation, submission, status and completion each need a narrower caller. None of these findings prove detached bb execution or establish whether existing operator contexts need migration.

## Findings by path

**1. Select and reserve A and B.** `executeCoreOperation` routes both `attempt.dispatch` and `attempt.continue` to `dispatch`. `dispatch` calls `Database.reserveAttempt` first for a preview, then for the write. The write is the useful boundary: `Database.write` starts `BEGIN IMMEDIATE`, runs a synchronous callback and commits. Inside that callback `reserveAttempt` selects by task position, checks for an existing attempt, counts all `execution_open` attempts in the database and inserts the reservation. `one_open_attempt_per_task` in `src/storage/schema.sql` also rejects a second open attempt. Keep that transaction pattern, ordering and uniqueness. `readyTasks()` alone is not safe for reservation: it is a snapshot, and it does not check capacity or existing attempts.

Implement a narrower reservation operation, not a wrapper that calls the old `dispatch`. Filter candidates by the requested objective for all callers; today the automatic scan is across tasks and objective filtering depends on the caller being a supervisor. Keep the capacity count project-wide. Replace the old admission blockers, budget checks and continuation inputs on this path. A stopped worker frees a slot even if its worktree is held; a task awaiting delivery must not thereby become eligible for another worker. Keep those two decisions separate. Preserve the independent-process automatic and named contention cases in `tests/cli-process/reservations-race.test.ts`; add contenders from two objectives sharing one limit. Preserve cycle rejection and ready order from `tests/operations/tasks.test.ts`.

**2. Allocate the worktree and hand off to bb.** `dispatch` calls `beginWorkspaceAcquisition`, `TreehouseWorkspace.acquire`, then `recordAllocation`, before it calls `prepareWorker`. The allocation and its lease identity are durable after `recordAllocation`, not merely because Treehouse returned a path. `prepareWorker` registers the owner, calls `launcher.prepare` and binds the confirmed reference with `Database.bindWorkerReference`; the latter writes `runtime_ref` and records `attempt.worker_bound`. Activation comes later. A stored thread reference therefore does not by itself mean the prompt was admitted. A lost create reply can leave a reservation and allocation but no usable thread ID.

Keep acquisition at the exact starting commit and the allocation and worker references. Reuse the bb command handling that distinguishes definite pre-create refusal from an uncertain reply. Replace the owner-dependent prepare/permit/activate sequence only once detached admission is demonstrated. Persist each submission outcome before returning; a lost reply must not become permission to submit again. After successful submission the new dispatcher returns instead of entering the `worker.wait` loop, refreshing claims, consuming questions, fencing and completing in `src/dispatch.ts`. Keep the exact-commit and wrong-holder cases in `tests/adapters/workspace.test.ts` and the lost-create case in `tests/adapters/bb.test.ts`. Add a process-exit test after submission; the existing mock tests cannot establish this property.

**3. Observe from a new process; keep status separate.** `BbLauncher.inspect` can read thread state and events by stored reference. Its `terminal` result also depends on this launcher's in-memory `stopped` and `fenced` collections. Those are not restored by reading `runtime_ref`. `BbLauncher.result` supplies a file path, not proof that a valid result exists. Also, `inspect` can fence on a workspace mismatch: it is not a harmless status read. Keep thread and event parsing behind the bb adapter. Do not persist a guess that an idle thread has released its worktree. The cases named ‘a recovering process’ and ‘idle is not terminal’ in `tests/adapters/bb.test.ts` show why the real two-process experiment is necessary. Since `ef336cd`, person recovery no longer depends on those in-memory sets: a thread with no running turn that is idle, errored or archived counts as stopped. That rule is a starting point for fresh-process observation, but it does not show that a later turn cannot start. Since `f93c30b`, `inspect` also accepts a thread whose environment record has been deleted (`path` null, status `destroyed`) as detached, and skips its path check in that case, so a deleted record no longer makes the worker unreadable.

`status.show` in `src/operations.ts` usually reads the database, but some branches call `leaseReturnReason` and `inspectWorkerOutput` through `services()`. Do not use that whole operation unchanged. Read task, attempt, allocation, stored worker reference and latest recorded observation; show unmet blocker IDs and the observation time. Have `sync` record observations and cleanup failures, not `status` calculate them by inspecting live resources. Keep the bounded history read tested by `tests/operations/status-performance.test.ts`. Add a status test with a held worktree and a runtime factory that throws if called. bb, Git and Treehouse need not be installed for that read.

**4. Check, deliver, unblock and return.** Today both `dispatch` and `observeWorker` can call `runCandidateChecks`; `acceptCandidate` also plans checks and integration. Keep trusted policy loading, exact-commit workspace inspection and `checkCommandRunner` in `src/adapters/checks.ts`. Give `sync` sole responsibility on the new path. Preserve the changed-workspace stop and exact passing-result reuse cases in `tests/operations/checks.test.ts`; replace tests whose sole prerequisite is a foreground owner. Readiness currently depends on `blocker.state = 'done'`. `Database.finishAcceptance` sets that state for manual acceptance as well as confirmed local integration; a person can also mark a task done. Do not equate either action with delivered code. For the new code-task workflow, record successful delivery before releasing dependants. Specify how a manual task decision affects code dependencies rather than inheriting an accidental bypass.

`acceptCandidate` already calls `GitRepository.conditionalFastForward` and uses `inspectRef` and `compare` to find out whether the target contains the commit. Reuse those operations, not the acceptance authorisation that encloses them. The person decision itself survives as the approval policy: keep binding the decision to the exact checked commit, but record it as an approval on the attempt rather than through the acceptance records. Preserve the non-fast-forward and moved-ref tests in `tests/adapters/repository.test.ts`. `returnAttempt` checks the recorded allocation against the live lease and inspects workspace cleanliness before `returnLease`. Keep those checks; adapt the return request if it would otherwise require an old acceptance record. Preserve the wrong-holder and lost-return-acknowledgement cases in `tests/adapters/workspace.test.ts`. Add an operation test where A integrates, return fails, C becomes ready, and a later sync retries cleanup without integrating again.

B requires new behaviour. `resolveReservationConfig` accepts `manual` or `local-merge`; the current reservation delivery contract is `review_or_integration`, not a per-task choice between fast-forward and PR. Add the project default and task override and store the resolved choice. Add PR publication and observation rather than treating manual acceptance as publication. The current dispatch reads `baseBranch` for the starting commit while delivery has a separate `targetBranch`. Ensure D actually starts from the refreshed target containing B, not just a configured base with the same name in the common case. Test that an open PR frees the lease but not D, and that a merged PR makes D eligible from the correct starting commit.

**5. Account for callers before removing anything.** Catalogue dispatch in `src/operations.ts` is not the only consumer: continuation uses the same `dispatch` and stays supported, so its starting-commit check moves to the new dispatch; manual acceptance and return use the completion services, and claim recovery can call `launcher.inspect`. The bb plugin in `bb/docket/plugin.ts` calls `host.bb-admit` and checks for it during setup. Preserve those routes for the current implementation until cutover; changing the adapter without changing the plugin would break admission. At cutover change the catalogue entries, their schemas, callers and tests together. Keep the submission/observation interface common to future launchers; `threadId`, held prompt admission and later-turn detection belong to bb. Retain bb plugin tests during the transition; replace the foreground dispatch expectation in `tests/cli-process/operations-dispatch-control.test.ts` with an independent process handoff test for the supported path.

## Decisions and what they wait for

- **Settled from the specification and source:** which DAG and task operations stay; where detached dispatch stops; which reads belong in status; which Git, Treehouse and check operations to reuse; which completion rules change. No replacement schema has been designed and no code removed.
- **Operator decision, settled:** start with freshly initialised contexts. No existing database, unfinished attempt or retained worktree carries over. Initialisation for the new workflow is to be documented; migration, resumption and automatic deletion of old contexts are not implemented.
- **Waiting for the bb experiment:** admission without an owner, finding a worker after a lost reply, and when the worktree can be reused. The [bb 0.49.0 qualification record](../qualification/bb-0.49.0.md) answers part of this, and [the detached specification](../specification/detached.md#bb-qualification-still-required) lists what remains, with manual confirmation as the fallback. If the worker cannot run independently at all, stop before implementing detached dispatch. Until the experiment has been run, do not adopt a particular bb admission mechanism or automatic worktree-return guarantee, and do not remove the existing guard.

The next code change is the detached bb experiment, not a broad refactor of storage or deletion of the old runner.
