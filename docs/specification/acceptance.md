# Acceptance scenarios

Status: draft, part of the [Docket specification](README.md). Every scenario is a required observable outcome unless its adapter/platform is explicitly outside the qualified release. Variants are parameterised cases, not a requirement for a complete end-to-end run per row.

Levels: P = pure decision/validation; O = in-process operations with real temporary SQLite and fake external owners; A = real adapter/protocol peer; C = essential cross-process/CLI; Q = host qualification; R = real everyday workflow.

All fault scenarios assert both the response and the persistent state/effect call count after reopening through a fresh operation. Waiting/races use barriers and an injected clock. A fake's “not called” assertion cannot replace the distinct real-process race/crash cases.

## Coverage and evidence rules

Implementation maintains a machine-readable mapping from each scenario to tests/qualification evidence, with pass/fail/unsupported and source commit, launcher and platform. A scenario may have several focused tests and one test may cover several scenarios. Every requirement R01–R40 appears above.

Synthetic tests prove mechanics, not model judgement, the resources a real provider loads, hardware power-loss durability or descendant termination. Real experiments state budget, versions, machine and observed limits. Skips for unavailable platforms/providers remain explicit qualification gaps. The required bb workflow cannot be skipped while declaring everyday-use release ready.
